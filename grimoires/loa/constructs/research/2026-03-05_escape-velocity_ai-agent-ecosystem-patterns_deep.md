### 2. Progressive Disclosure of Context

**Problem Solved:** Overcoming context window limits, reducing token usage, and improving AI accuracy by providing *only* relevant information to the AI *exactly* when it needs it. This prevents the AI from being overwhelmed by irrelevant data, reducing noise and hallucination.

**Technique:** Dynamically loading and injecting agent rules, constructs, or contextual documents based on the current project context, active file, keywords in the user's prompt, or explicit mentions. This is a system-level capability, but authors design their constructs to leverage it.

**Why it matters:**
*   **Token Savings & Cost Reduction:** Significantly reduces the amount of text sent to the LLM, leading to lower API costs and faster inference times.
*   **Improved AI Accuracy & Focus:** Less irrelevant context means less "noise" for the AI, allowing it to focus on the task at hand, reducing hallucination, and improving the quality of its responses.
*   **Scalability:** Enables the creation of a vast library of constructs and rules without overwhelming the AI on any single task. The system can manage hundreds or thousands of rules, but only a handful are active at any given moment.
*   **Enhanced Developer Experience:** The AI feels more intelligent and "aware" of the specific project and task, requiring less explicit guidance from the user.

**Complete Implementation (Conceptual - Design Pattern for Authors):**

This technique is primarily implemented by the AI assistant's core orchestration logic (e.g., Cursor's rule engine, Claude Code's command loader). However, the *design pattern* for construct authors is crucial for making their constructs progressively discoverable.

1.  **Structured Rule Organization:**
    *   Organize constructs/rules in a nested, semantic directory structure (e.g., `.constructs/frontend/react`, `.constructs/backend/nodejs`, `.constructs/testing/jest`). This provides a hint to the system about the domain of the rule.
2.  **Precise Activation Conditions (`globs`):**
    *   Within the YAML frontmatter of `.mdc` or `.md` files, define highly specific `globs` patterns. These patterns tell the system exactly which file types or paths make the rule relevant.
    *   Example: `globs: ['src/components/**/*.tsx', 'src/pages/**/*.tsx']` for a React component rule.
3.  **Project Markers & Heuristics:**
    *   The AI system detects the overall project context by looking for common project markers (e.g., `package.json` for Node.js, `pyproject.toml` for Python, `webpack.config.js` for frontend, `Dockerfile`). This activates broad categories of rules.
4.  **Keyword Matching & Semantic Search:**
    *   The system analyzes the user's prompt and the current task for keywords (e.g., "create React component," "fix database query," "deploy to production"). It might also use embeddings to semantically search for relevant constructs.
5.  **Dynamic Loading & Injection:**
    *   Based on the combination of active file, project context, `globs` matches, and prompt keywords, the orchestrator *only* injects the most relevant `.mdc` files or construct definitions into the AI's context window for the current turn. Irrelevant rules are filtered out.

### 4. Model Context Protocol (MCP) Server Design for Tools

**Problem Solved:** Standardizing how AI agents interact with external data, tools, and services, moving beyond static training data to dynamic, real-time information and actions. MCP enables secure, composable, discoverable, and intent-driven tool integration, allowing AI to perform actions in the real world.

**Technique:** Building focused, composable MCP servers that expose well-defined tool interfaces with clear JSON Schemas and metadata. These servers communicate with the AI orchestrator via `stdio` (standard input/output) for local, secure, and fast interactions, adhering to the JSON-RPC 2.0 specification.

**Why it matters:**
*   **Standardization & Interoperability:** MCP provides a universal "language" (JSON-RPC 2.0 over stdio) for AI agents to communicate with external capabilities, regardless of the underlying programming language or service.
*   **Composability:** Encourages the creation of small, focused servers, each exposing a limited set of related tools. These can then be combined and orchestrated to build complex, multi-tool workflows.
*   **Discoverability & Reasoning:** Servers advertise their capabilities through structured JSON Schemas for each tool's input and output. This allows the AI to understand *what* a tool does, *what* inputs it requires, and *what* output to expect, enabling sophisticated tool-use reasoning.
*   **Security & Performance:** Using `stdio` for local communication is inherently secure (no network ports exposed) and extremely fast, making it ideal for tight integration with local AI coding assistants.
*   **Intent-Driven Design:** Tools are designed around user intents (e.g., `getWeather`, `createReactComponent`), abstracting away the low-level API calls. This makes the tools easier for the AI to understand and use effectively, reducing hallucination.
*   **Real-time Data & Actions:** Allows AI agents to fetch current information (e.g., file contents, API responses) and perform actions (e.g., run tests, deploy code) that are beyond their static training data.

**Common Pitfalls & How Experts Avoid Them:**
*   **Poorly Defined Schemas:** Amateurs use vague descriptions or no schemas, leading to AI hallucinating inputs or misinterpreting outputs. Professionals use robust schema validation libraries (like Zod in TypeScript, Pydantic in Python) to define precise input/output contracts, including `description`, `min/max`, `enum`, and `required` fields.
*   **API-Centric Tool Design:** Amateurs expose raw API calls (e.g., `weatherApi.fetchForecastByLatLong`). Professionals design tools around user intents (e.g., `getWeather`), abstracting away low-level details and making them easier for the AI to reason about.
*   **Lack of Security & Validation:** Amateurs trust AI inputs implicitly. Professionals implement robust parameter validation within the `run` method and leverage schema validation to prevent invalid or malicious inputs.
*   **Monolithic Servers:** Amateurs build one giant server for all tools. Professionals build small, focused servers for specific domains (e.g., `weather-server`, `git-server`, `file-system-server`) to maximize composability and maintainability.
*   **Inadequate Logging:** Amateurs don't log tool calls. Professionals log all incoming requests and outgoing responses to `stderr` (to avoid interfering with `stdout` which is for MCP communication) for debugging and auditing.
*   **Blocking Operations:** Amateurs might perform long-running synchronous operations in `run`. Professionals ensure `run` methods are `async` and handle long-running tasks gracefully, potentially returning immediate status and using callbacks or polling for completion.

### 5. LangSmith Prompt Versioning & Evaluation Loop

**Problem Solved:** Managing the lifecycle of prompts as first-class software artifacts, enabling Git-style version control, systematic testing, and continuous improvement. This replaces ad-hoc prompt tweaking with a robust, data-driven methodology.

**Technique:** Using LangSmith (or similar platforms like Hugging Face Hub for models/datasets) for Git-style versioning of prompts (commits, tags like `dev`, `staging`, `prod`), programmatic management via SDKs, and integrating prompts into a continuous evaluation and feedback loop. This involves creating datasets, running evaluations, and comparing prompt versions.

**Why it matters:**
*   **Reproducibility:** Ensures you know exactly which prompt version was used for any given AI interaction, crucial for debugging and auditing.
*   **Reliability & Regression Prevention:** Catch regressions early through automated evaluations against predefined datasets and metrics. Prevents a "working" prompt from breaking due to subtle changes.
*   **Collaboration & Governance:** Teams can share, review, and promote prompt versions through a structured workflow, similar to code reviews.
*   **Data-Driven Optimization:** Use metrics, A/B testing, and human feedback to systematically optimize prompt performance, leading to better AI outputs and efficiency.
*   **Decoupling & Hot-Fixing:** Prompts can be updated and deployed independently of application code, allowing for rapid iteration and hot-fixes without full application redeployments.

    try:
        client.push_prompt(
            repo_name=repo_name,
            object=prompt_object,
            new_repo_is_public=is_public

    repo_name="constructs-network/career-advisor-v1", # Use "org/repo-name" for private repos

    is_public=False # Set to True if you want it public on LangChain Hub

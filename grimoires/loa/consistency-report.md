# Consistency Report — loa-constructs

> Generated by /ride 2026-05-05. Pattern analysis across naming, structure, and conventions.
> Methodology: flag breaking changes; never implement. Score 1-10 (10 = consistent).

## Score: 7.5 / 10

The codebase shows strong, mostly-consistent conventions, with a handful of accumulated naming drift points that are visible but not blocking.

## Naming consistency

### Routers

Convention: `XxxRouter` (named export). Examples: `subscriptionsRouter`, `webhooksRouter`, `skillsRouter`, `teamsRouter`, `analyticsRouter`, `creatorRouter`, `creatorsRouter`, `auditRouter`, `packsRouter`, `signalsRouter`, `constructsRouter`, `categoriesRouter`, `adminRouter`, `keysRouter`, `publicKeysRouter`, `docsRouter`.

**Outliers** (use bare camelCase, not `Router` suffix):
- `health` (app.ts:8)
- `auth` (app.ts:9)
- `oauth` (app.ts:10)
- `dynamicAuth` (app.ts:11)

**Decision needed**: rename outliers to `healthRouter`, `authRouter`, `oauthRouter`, `dynamicAuthRouter`, OR strip suffix from the rest. **Score impact: -0.5**.

### Tables

Convention: camelCase Drizzle export → snake_case SQL table.
- `users`, `teams`, `teamMembers`, `apiKeys`, `skillVersions`, `packVersions`, `packFiles`, `packSyncEvents`, `constructIdentities`, `constructVerifications`, `constructReviews`, `constructShowcases`, `signalOutcomes`, `creatorPayouts`, `graduationRequests`, `auditLogs`, `githubWebhookDeliveries`, `categories`, etc.

**Score**: clean, fully consistent.

### Tests

Convention: `<file>.test.ts` colocated next to source.
- `auth.test.ts` next to `auth.ts`
- `categories.test.ts` next to `categories.ts`

Plus: `apps/api/src/lib/__tests__/` and `packages/shared/src/__tests__/` directories also exist for grouped tests. Both patterns coexist.

**Decision needed**: pick colocation OR `__tests__/`, not both. **Score impact: -0.5**.

### Migration files

Convention: numbered SQL files in `apps/api/src/db/migrations/` (8 files). Aligned.

## Structural consistency

### Workspace boundaries

Each workspace has its own:
- `package.json` with private:true
- `tsconfig.json` (likely extends root `tsconfig.base.json`)
- `vitest` config (but **3 different vitest majors** — see hygiene-report.md)

**Score impact: -0.5** for vitest version drift.

### Dependency injection vs. module-scope state

Most `services/*.ts` are pure module-scope functions taking a `db` argument or pulling from a singleton (`db/index.ts`). No DI container observed. This is consistent across services.

Mock DB (`db/mock.ts`) swaps the singleton when `DEV_MOCK_DB=true`. Consistent strategy.

### Middleware factory pattern

All middleware export a factory function:
```ts
export const requestId = () => async (c, next) => { ... }
```
vs. `maintenanceMode` exported as the middleware itself (no factory). Minor inconsistency. **Score impact: -0.25**.

## Pattern conflicts

### Two `visibility-guard.ts` modules

- `apps/api/src/lib/visibility-guard.ts` (cross-cutting helper)
- `apps/api/src/services/visibility-guard.ts` (DB-aware guard)

Same name, different layers. Either rename or document the boundary explicitly. **Score impact: -0.5**.

### `routes/skills.ts` vs `routes/packs.ts`

Both exist, both extensively wired. The pack model (cycle-007 era) appears to have superseded the skill model (per CHANGELOG-implied evolution), but skill routes are still mounted (`v1.route('/skills', skillsRouter)` in app.ts:116). Likely kept for backwards compat.

**Decision needed**: verify intentional dual-API and either consolidate or document deprecation timeline. **Score impact: -0.5**.

### Hono context typing

`app.ts` declares `type Variables = { requestId: string }` (line 37) and types the app as `new Hono<{ Variables: Variables }>()` (line 42). But routes use `c.get('userId')`, `c.get('user')`, `c.get('teamId')` etc. — none of which are in `Variables`.

**Decision needed**: extend `Variables` to include `userId`, `user`, `teamId`, etc. — currently relying on untyped `c.get` casts and one `as never` cast in admin.ts:1074. **Score impact: -0.5** (typing escape hatches).

## Improvement opportunities

| Opportunity | Impact | Risk |
|-------------|--------|------|
| Rename `auth`, `oauth`, `health`, `dynamicAuth` → `*Router` for consistency | Low (cosmetic) | Low — rename only |
| Pick test colocation pattern (kill `__tests__/` or kill colocation) | Medium (codebase clarity) | Low |
| Pin vitest to one major across workspaces | High (test reliability) | Low |
| Type Hono `Variables` to include all `c.set` keys | High (compile-time safety) | Medium — flushes out hidden type errors |
| Consolidate or document the two `visibility-guard.ts` modules | Medium (mental load) | Low |
| Decide skill API deprecation status; document timeline | High (consumer clarity) | Medium |

## Breaking changes flagged (NOT implemented)

1. Renaming `auth` → `authRouter` would touch every consumer in tests; safe rename but big diff.
2. Removing `__tests__/` directories would require moving 5+ files.
3. Removing `routes/skills.ts` would break the `/v1/skills` API consumers (third-party CLI installs likely depend on this).
4. Pinning vitest would force regen of all `vitest` config types in shared/loa-registry.

**No changes made**. All flagged for human decision.

# World Architecture — The Modular World Pattern

> Universal architecture for sovereign stack projects. Both sprawl-protocol and project-purupuru
> follow this pattern. Any new world follows it too.

**Date**: 2026-03-31
**Constraint**: $5/mo per world on Railway. Own everything. One agent sees everything.

---

## The Pattern

A **world** is a single repo containing a SvelteKit app with embedded modules. Each module has clear boundaries (own directory, own types, own tests) but shares one database and one deploy.

Railway shows you all the modules as one service. You interact with Railway's UI to see logs, metrics, deploys — one service per world, not N services per world.

```
┌─────────────────────────────────────────────────┐
│                   RAILWAY                        │
│                                                  │
│   ┌───────────────────────────────────────┐     │
│   │          your-world (service)          │     │
│   │                                        │     │
│   │   SvelteKit ──── Turso (SQLite file)  │     │
│   │      │                    │            │     │
│   │      ├── routes/    ← UI rooms        │     │
│   │      ├── lib/score/ ← scoring engine  │     │
│   │      ├── lib/wire/  ← data pipeline   │     │
│   │      ├── lib/puru/  ← design system   │     │
│   │      ├── evals/     ← AI quality      │     │
│   │      └── crons      ← in-process jobs │     │
│   │                                        │     │
│   └───────────────────────────────────────┘     │
│                                                  │
│   Volume: /data/world.db (persistent SQLite)     │
│   Cost: $5/mo                                    │
└─────────────────────────────────────────────────┘
```

One service. One database file. One deploy. One agent context.

## Module Boundaries

Each module is a directory with a clear public API (`index.ts`). The rule: **modules can import from `db/` but not from each other.**

```
routes/ ──→ lib/score/    (rooms use score)
routes/ ──→ lib/wire/     (rooms use data)
routes/ ──→ lib/design/   (rooms use components)
routes/ ──→ lib/db/       (rooms query directly too)

lib/score/ ──→ lib/db/    (score reads/writes DB)
lib/wire/  ──→ lib/db/    (pipeline reads/writes DB)

lib/score/ ✗→ lib/wire/   (score does NOT import wire)
lib/wire/  ✗→ lib/score/  (wire does NOT import score)
```

if score needs wire data, it reads from the database — not by importing wire. the database IS the integration point. this prevents coupling while keeping everything in one repo.

## What Stays Separate (and Why)

| Repo | Why separate |
|------|-------------|
| **contracts** (per world) | Different toolchain (Foundry/Solidity), different deploy target (Base/Berachain), different CI. World imports ABIs, not source. |
| **game** (purupuru only) | Gumi's domain. Game engine logic ships as a package world imports. Gumi works independently. |
| **loa** | Framework. Mounted in every world via `.claude/`. Not a world itself. |
| **constructs** (loa-constructs) | The marketplace/registry. Separate product, separate stack (currently Next.js). |

Everything else collapses into the world repo.

## Migration Order

For both sprawl and purupuru, the migration is:

### Step 1: Convex → Turso (the database)
Follow `sovereign-stack-kickoff.md`. This is the prerequisite — nothing else moves until the database is local.

### Step 2: Score → src/lib/score/ (the brain)
Copy score repo's logic into the world. Point it at Turso instead of its own database. Delete network calls, replace with Drizzle queries.

### Step 3: Wire/Sonar → src/lib/wire/ (the ears)
Copy ingestion logic into the world. Crons run in-process. Data lands in the same SQLite file.

### Step 4: Design → src/lib/design/ or src/lib/puru/ (the skin)
Copy design tokens, components, springs into the world. If it's just CSS + a few components, this is trivial.

### Step 5: Eval → evals/ (the eyes)
Copy fukuro/observatory into evals/. Point at Turso. Same process reads same data.

### Step 6: Archive old repos
Don't delete. Archive on GitHub. They're the history. The world repo is the future.

## For New Worlds

Any new project (apHive, pyonpyon, future products) starts with this structure from day one:

```bash
bun create svelte@latest my-world
cd my-world
bun add drizzle-orm @libsql/client viem
bun add -d drizzle-kit

# Create the module directories
mkdir -p src/lib/{db,score,wire,design} evals scripts mcp drizzle data grimoires
```

Install constructs:
```bash
npx loa-cli install artisan protocol rosenzu the-arcade
```

Write `CLAUDE.md`:
```markdown
# [World Name]

This is a sovereign stack world: SvelteKit 5 + Turso/Drizzle + Railway.

## Modules
- src/lib/db/ — Turso/Drizzle database
- src/lib/score/ — scoring engine
- src/lib/wire/ — data pipeline
- src/lib/design/ — design system

## Stack
SvelteKit 5, Turso embedded replica, Drizzle ORM, Railway, viem, vanilla wallet.
```

Deploy to Railway:
```bash
railway init
railway volume add --mount /data
railway up
```

$5/mo. Done.
